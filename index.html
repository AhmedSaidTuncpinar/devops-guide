Bu rehberi çalıştırmak için WSL2, VS Code, Docker Desktop, Git, Node.js, kubectl, minikube, Terraform ve AWS CLI gereklidir. Aşağıdaki adımları sırayla tamamla — her araç bir sonraki gün için zemin hazırlar.

Bölüm 1 — WSL2 Kur (Sadece Windows Kullanıcıları)

WSL2 = Windows içinde gerçek Linux kernel. Docker, Kubernetes ve tüm araçlar burada çalışır. Mac/Linux kullanıyorsan bu bölümü atla.

  1. PowerShell'i Yönetici olarak aç ve WSL2'yi tek komutla kur. Windows PowerShell — Admin
    wsl --install
    ✓ Kurulum tamamlanınca bilgisayarı yeniden başlat. Ubuntu terminali otomatik açılır ve kullanıcı adı ile şifre oluşturman istenir.
  2. Versiyonu doğrula ve WSL2'yi varsayılan yap. Windows PowerShell
    wsl --list --verbose
wsl --set-default-version 2
    ✓ Ubuntu ... Running 2 görürsün. VERSION sütununda 2 yazmalı — 1 yazıyorsa yukarıdaki komut ayarlamıştır.
Bölüm 2 — VS Code + Remote WSL Extension

VS Code'u Windows'a kur, Remote WSL ile WSL içindeki dosyaları düzenle. Bu kombinasyon Windows Terminal yerine önerilen geliştirme ortamı.

  1. VS Code'u kur — kurulumda "Add to PATH" seçeneğini işaretle. Tarayıcı
    https://code.visualstudio.com/download
    Kurulum sihirbazında "Add to PATH (available after restart)" kutusunu işaretle. Ardından PowerShell'de doğrula: 
    code --version
    ✓ Versiyon numarası döner, örnek: 1.92.0
  2. Remote WSL extension'ı kur. PowerShell veya VS Code Terminali
    code --install-extension ms-vscode-remote.remote-wsl
    ✓ Extension 'ms-vscode-remote.remote-wsl' was successfully installed.
  3. WSL terminalinden VS Code'u aç. WSL — Ubuntu Terminali
    cd ~
code .
    ✓ VS Code açılır, sol alt köşede yeşil >< WSL: Ubuntu ibaresi görünür. Artık tüm kodlama bu pencerede yapılır — terminali VS Code içinden aç (Ctrl+J).
Bölüm 3 — Docker Desktop (WSL2 Backend)

Docker Desktop'ı Windows'a kur ama WSL2 üzerinden çalışmasını sağla — bu sayede WSL terminalinde docker komutları doğrudan çalışır.

  1. Docker Desktop'ı indir ve kur. Tarayıcı
    https://www.docker.com/products/docker-desktop
    Kurulum sihirbazını çalıştır. Kurulum sırasında "Use WSL 2 instead of Hyper-V" seçeneği otomatik işaretli gelmeli.
  2. WSL entegrasyonunu etkinleştir. Docker Desktop — Settings
    Docker Desktop'ı aç → Settings → General → "Use the WSL 2 based engine" ✓
    → Settings → Resources → WSL Integration → Ubuntu distro'nu açık konuma getir ✓
    → Apply & Restart butonuna bas.
  3. WSL içinden Docker'ı doğrula. WSL — Ubuntu Terminali
    docker --version
docker compose version
docker run --rm hello-world
    ✓ Hello from Docker! mesajını görürsün. Bu noktaya geldiysen Docker çalışıyor.
Bölüm 4 — Git: Kurulum ve Global Yapılandırma

WSL Ubuntu'ya Git genellikle kurulu gelir. Versiyonu kontrol et, eksikse kur ve kimliğini tanımla.

  1. Git versiyonunu kontrol et, kurulu değilse kur. WSL — Ubuntu Terminali
    git --version
sudo apt update && sudo apt install -y git
    ✓ git version 2.x.x görürsün.
  2. Global kimlik ve editör ayarlarını yap — bu ayarlar tüm projelere uygulanır.
    git config --global user.name "Adın Soyadın"
git config --global user.email "senin@email.com"
git config --global init.defaultBranch main
git config --global core.editor "code --wait"
git config --list | grep -E "user\.|init\.|core\."
    ✓ Dört satır yapılandırma listede görünür.
Bölüm 5 — Node.js (nvm ile)

nvm = Node Version Manager. Birden fazla Node versiyonunu kolayca yönetir. Platform-ops projesi Node 20 LTS üzerinde çalışır.

  1. nvm kur ve terminale yükle.
    curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
source ~/.bashrc
nvm --version
    ✓ 0.39.7 görürsün. Görmüyorsan terminali kapat/aç ve tekrar dene.
  2. Node.js 20 LTS'yi kur ve varsayılan yap.
    nvm install 20
nvm use 20
nvm alias default 20
node --version
npm --version
    ✓ v20.x.x ve 10.x.x görürsün.
Bölüm 6 — kubectl ve minikube (Kubernetes Günü İçin)

Kubernetes bölümünde kullanılacak. Şimdi kurulumu tamamla, günü gelince hazır olsun.

  1. kubectl kur — Kubernetes cluster'ını yönetmek için komut satırı aracı.
    curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"

    curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
chmod +x minikube-linux-amd64
sudo mv minikube-linux-amd64 /usr/local/bin/minikube

    ✓ minikube version: v1.32.x görürsün.
Bölüm 7 — Terraform (Terraform Günü İçin)

HashiCorp'un resmi apt deposu üzerinden kurulur. Bu yöntemle apt upgrade ile otomatik güncelleme yapılabilir.

  1. HashiCorp GPG anahtarını ve deposunu ekle, Terraform'u kur.
    sudo apt update && sudo apt install -y gnupg software-properties-common wget
wget -O- https://apt.releases.hashicorp.com/gpg | \
  sudo gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] \
  https://apt.releases.hashicorp.com $(lsb_release -cs) main" | \
  sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt update && sudo apt install -y terraform
terraform version
    ✓ Terraform v1.5.x görürsün.
Bölüm 8 — AWS CLI v2 (AWS Günü İçin)

AWS CLI v2'yi resmi installer ile kur. Paket yöneticisi versiyonları eski kalabilir — bu yöntem her zaman güncel sürümü getirir.

  1. AWS CLI v2'yi indir, kur ve geçici dosyaları temizle.
    sudo apt install -y unzip curl
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "/tmp/awscliv2.zip"
unzip /tmp/awscliv2.zip -d /tmp/awscli-setup
sudo /tmp/awscli-setup/aws/install
rm -rf /tmp/awscliv2.zip /tmp/awscli-setup
aws --version
    ✓ aws-cli/2.x.x Python/3.x.x Linux/x86_64 görürsün.

Yaygın Sorunlar ve Çözümleri
Docker: "Cannot connect to the Docker daemon"

Docker Desktop kapalı veya WSL entegrasyonu aktif değil.

Docker Desktop aç → Settings → Resources → WSL Integration → Ubuntu aç → Apply & Restart
nvm: "command not found" (terminali kapatıp açtıktan sonra)

nvm satırları ~/.bashrc'ye eklendi ama terminal yeniden yüklenmedi.

source ~/.bashrc
grep "nvm" ~/.bashrc | head -3
kubectl veya minikube: "Permission denied" ya da "not found"

Binary /usr/local/bin yerine yanlış konuma kopyalandı.

ls -la /usr/local/bin/kubectl /usr/local/bin/minikube
which kubectl && kubectl version --client
Terraform: "command not found" apt install sonrasında

apt deposu eklenmeden önce apt update yapılmamış olabilir.

sudo apt update && sudo apt install -y terraform
terraform version
AWS CLI: "aws: command not found" install sonrasında

Installer /usr/local/bin'e kurar ama mevcut terminal oturumu PATH'i yenilemiş olmayabilir.

hash -r && aws --version
which aws
VS Code: "code ." WSL'den açmıyor

VS Code kurulumunda PATH seçeneği işaretlenmedi veya Remote WSL extension eksik.

code --install-extension ms-vscode-remote.remote-wsl
ls ~/.vscode-server/bin/ 2>/dev/null | head -3 || echo "WSL server henüz kurulmadı — code . ile kurulur"

Hikaye

Sabah 08:00, ofise geldin. Ekip senden sunucunun sabah kontrolünü yapmanı istedi. Uygulama yavaş çalışıyor diye şikayet var. Docker container'ına bağlan, aşağıdaki adımları sırayla yap. Her adımda komutu çalıştır ve çıktısını anlamlandır.

Bölüm 1 — Neredesin, Ne Var? (B1)
  1. Container'a bağlan. Hangi klasördesin?
  2. /project klasörünü listele — kaç dosya ve klasör var? (gizliler dahil)
  3. /project/tests/specs içine gir, kaç spec dosyası var?

D1 Temel Kavramlar Docker ▼

Docker, bir uygulamayı ve onun ihtiyaç duyduğu her şeyi — kod, çalışma ortamı, kütüphaneler, ayarlar — container adı verilen tek bir pakete koymanı sağlar. Bu container her makinede aynı şekilde çalışır. "Bende çalışıyor ama sunucuda çalışmıyor" sorunu biter.

Temel Kavramlar
Image      → salt okunur şablon. Tarif gibi.
Container  → image'dan başlatılan çalışan kopya. Pişirilen yemek gibi.
Registry   → image deposu (Docker Hub, AWS ECR, GitHub Container Registry)
Layer      → Dockerfile'daki her satır image'a bir katman ekler
Volume     → container dışında tutulan kalıcı veri
Network    → container'ların birbiriyle konuşma yöntemi
Benzetme
Image      → tarif kartı
Container  → o tariften pişirilen yemek
Registry   → tarif kitabı (Docker Hub)

Docker Olmadan vs Docker ile
Docker olmadan:
  "Bende çalışıyor" — farklı işletim sistemi, farklı Node sürümü,
  farklı kütüphane sürümleri → sadece sunucuda çıkan hatalar

Docker ile:
  geliştirici image oluşturur → registry'e gönderir
  sunucu aynı image'ı çeker → özdeş ortamda çalıştırır
  her yerde aynı davranış garantisi

C1 Temel Kavramlar CI/CD ▼
CI/CD Nedir?
CI — Sürekli Entegrasyon (Continuous Integration)
     Kod her push'landığında otomatik olarak test edilir.
     Testler başarısız olursa ekip anında haberdar edilir.

CD — Sürekli Teslimat / Dağıtım (Continuous Delivery / Deployment)
     Testler geçtikten sonra kod otomatik olarak
     derlenir, paketlenir ve bir ortama dağıtılır.
CI/CD Olmadan vs CI/CD ile
CI/CD olmadan:
  geliştirici kod yazar
  → testleri manuel çalıştırır (veya unutur)
  → uygulamayı manuel derler
  → sunucuya manuel dağıtır
  → hiçbir şeyin bozulmamasını umar

CI/CD ile:
  geliştirici kodu push'lar
  → pipeline otomatik çalışır
  → testler, linting, derleme çalışır
  → hepsi geçerse → otomatik dağıtım
  → herhangi biri başarısız olursa → geliştirici bilgilendirilir

Kubernetes — 7 Bölüm
K1 Temel Kavramlar Kubernetes ▼

Docker tek bir makinede tek container çalıştırır. Kubernetes ise yüzlerce makine üzerinde binlerce container'ı çalıştırır — ve bunları otomatik olarak yönetir. Container'larını başlatmayı, durdurmayı, ölçeklendirmeyi, iyileştirmeyi ve ağ bağlantısını manuel yapmak zorunda kalmazsın.

Kubernetes'in Çözdüğü Problem
Kubernetes olmadan:
  10 sunucun var
  hangi container'ın hangi sunucuda çalışacağına manuel karar veriyorsun
  bir sunucu çöküyor → container'ları başka sunucuda manuel yeniden başlatıyorsun
  trafik artıyor → daha fazla container'ı manuel başlatıyorsun
  yeni sürüm → her container'ı tek tek manuel güncelliyorsun

Kubernetes ile:
  ne istediğini tanımlarsın: "bu container'dan 5 kopya çalıştır"
  Kubernetes nerede çalıştıracağına karar verir
  bir node çöküyor → Kubernetes container'ları başka node'da otomatik yeniden başlatır
  trafik artıyor → Kubernetes otomatik ölçeklendirir (HPA)

K2 Mimari Kubernetes ▼

Kubernetes cluster'ının iki tür makinesi vardır: Control Plane (beyin) ve Worker Node'lar (kas). Bunlara doğrudan dokunmazsın — kubectl aracılığıyla Control Plane ile konuşursun, geri kalanını o halleder.

Cluster Mimarisi

│                   CONTROL PLANE                      │
│                                                      │
│  API Server    ← kubectl buraya konuşur              │
│  etcd          ← cluster durum veritabanı            │
│  Scheduler     ← hangi node'un hangi pod'u çalıştıracağına karar verir │
│  Controller    ← durumu izler, farkları düzeltir     │
└──────────────────────────┬──────────────────────────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
   ┌──────▼──────┐  ┌──────▼──────┐  ┌─────▼───────┐
   │  WORKER     │  │  WORKER     │  │  WORKER     │
   │  NODE 1     │  │  NODE 2     │  │  NODE 3     │
   │             │  │             │  │             │
   │  kubelet    │  │  kubelet    │  │  kubelet    │
   │  kube-proxy │  │  kube-proxy │  │  kube-proxy │
   │  pod'lar... │  │  pod'lar... │  │  pod'lar... │

Control Plane Bileşenleri
BileşenNe yapar
API ServerÖn kapı. Tüm kubectl komutları buraya gelir. İstekleri doğrular ve işler.
etcdAnahtar-değer veritabanı. Tüm cluster durumunu depolar. Gerçeğin kaynağı.
SchedulerAtanmış node'u olmayan yeni Pod'ları izler. Çalıştırmaları için en iyi node'u seçer.
Controller ManagerKontrol döngüleri çalıştırır. İstenen durumu gerçek durumla karşılaştırır. Farkları düzeltir.
Worker Node Bileşenleri
BileşenNe yapar
kubeletHer node'daki ajan. API Server ile konuşur. Container'ları başlatır ve durdurur.
kube-proxyNode'daki ağ kurallarını yönetir. Trafiği doğru Pod'a yönlendirir.
Container RuntimeContainer'ları gerçekten çalıştırır. Genellikle containerd (modern K8s'te artık Docker değil).
Kubectl Komutunun Akışı
çalıştırırsın: kubectl apply -f deployment.yaml

1. kubectl → API Server (YAML'ı gönderir)
2. API Server → etcd (istenen durumu kaydeder)
3. Controller Manager → yeni Deployment görür, ReplicaSet oluşturur
4. ReplicaSet → 3 Pod oluşturur
5. Scheduler → her Pod'u bir Node'a atar
6. Node'daki kubelet → image'ı çeker, container başlatır
7. kube-proxy → Service için ağ kurallarını ayarlar

K4 İş Yükleri — Pod, Deployment, ReplicaSet Kubernetes ▼

İş yükleri container'larını çalıştıran kaynaklardır. Pratikte neredeyse hiçbir zaman doğrudan Pod oluşturmazsın — Deployment oluşturursun, o ReplicaSet oluşturur, o da Pod'ları oluşturur. Bu zinciri anlamak şarttır.

Pod — En Küçük Birim
# pod.yaml — production'da nadiren doğrudan kullanılır
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  labels:
    app: web
spec:
  containers:
    - name: web
      image: nginx:1.25
      ports:
        - containerPort: 80
      resources:
        requests:
          memory: "64Mi"
          cpu: "250m"      # 250 millicore = 0.25 CPU
        limits:
          memory: "128Mi"
          cpu: "500m"
Neden Pod'ları Doğrudan Kullanmıyoruz?
# manuel Pod oluşturur ve çökerse:
# → öylece kalır. Kimse yeniden başlatmaz.

# 3 replikalı Deployment oluşturur ve bir Pod çökerse:
# → ReplicaSet yalnızca 2'sinin çalıştığını saptar
# → anında yedek Pod oluşturur
# → her zaman 3 tanesi çalışır
Deployment — Gerçekten Kullandığın Şey
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  namespace: default
spec:
  replicas: 3                    # 3 kopya çalıştır
  selector:
    matchLabels:
      app: web                   # bu etikete sahip pod'ları yönet
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1          # güncelleme sırasında en fazla 1 pod kapalı
      maxSurge: 1                # güncelleme sırasında en fazla 1 ekstra pod
  template:                      # pod şablonu — her pod böyle görünür
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.25
          ports:
            - containerPort: 80
          readinessProbe:         # pod hazır olduğunda trafiği gönder
            httpGet:
              path: /health
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:          # pod sağlıksız olursa yeniden başlat
            httpGet:
              path: /health
              port: 80
            initialDelaySeconds: 15
            periodSeconds: 20
ReplicaSet — Orta Katman
Deployment → ReplicaSet'leri yönetir (sürüm başına bir tane)
ReplicaSet → Pod'ları yönetir (doğru sayıyı sağlar)
Pod        → container'ını çalıştırır

# Deployment'ı sen tanımlarsın. Kubernetes ReplicaSet ve Pod'ları yönetir.
# rolling update sırasında:
#   eski ReplicaSet küçülür
#   yeni ReplicaSet büyür
#   Deployment hızı kontrol eder

K6 Config ve Depolama Kubernetes ▼

Container'larının config'e ihtiyacı var — veritabanı URL'leri, özellik bayrakları, API anahtarları. Kubernetes hassas olmayan config için ConfigMap, hassas veriler için Secret sağlar. Kalıcı depolama için PersistentVolume'lar verileri Pod silinse bile canlı tutar.

ConfigMap — Hassas Olmayan Config

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  NODE_ENV: production
  LOG_LEVEL: info

---
# Pod'da kullan — ortam değişkenleri olarak
spec:
  containers:
    - name: web
      image: myapp:1.0
      envFrom:
        - configMapRef:
            name: app-config      # tüm anahtarları env var olarak enjekte et

# veya tek tek seç:
      env:
        - name: NODE_ENV
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: NODE_ENV

T1 Terraform Nedir? Terraform ▼

Terraform, altyapını kod olarak tanımlamana yarayan bir araçtır. Sunucu oluşturmak, ağ kurmak, veritabanı açmak — bunları elle yapmak yerine bir dosyaya yazarsın, Terraform halleder. Bu yaklaşıma Infrastructure as Code (IaC) denir.

Elle Altyapı vs Terraform ile Altyapı
Elle yapıldığında:
  AWS konsoluna gir → EC2 sayfasına git → "Launch Instance" tıkla
  → instance tipi seç → güvenlik grubu ayarla → başlat

  → başka ortamda aynısını yapmak 30 dakika sürer

  main.tf dosyasına yaz → terraform apply
  → aynı altyapı her seferinde aynı şekilde oluşur
  → git geçmişinde ne değiştiği görünür
  → staging ile production aynı kod, farklı değişkenler
  → sil, tekrar aç — dakikalar içinde

T5 Modüller Terraform ▼

Modül, tekrar kullanılabilir Terraform kod paketidir. Bir VPC kurulumu veya EC2 + güvenlik grubu kombinasyonu — bunları her ortam için sıfırdan yazmak yerine bir modüle koyarsın, her yerde çağırırsın. Git'teki fonksiyon mantığının altyapı hali.

Modülsüz vs Modüllü
# MODÜLSÜZ — staging ve production için ayrı ayrı yaz
# staging/main.tf
resource "aws_instance" "web" { instance_type = "t3.micro" ... }

# production/main.tf — aynı kodu tekrar yaz
resource "aws_instance" "web" { instance_type = "t3.large" ... }

module "staging_web" {
  source         = "./modules/web-server"
  instance_tipi  = "t3.micro"
  ortam          = "staging"
}

module "production_web" {
  source         = "./modules/web-server"
  instance_tipi  = "t3.large"
  ortam          = "production"
}

AWS (Amazon Web Services), dünyanın en büyük bulut sağlayıcısıdır. Kendi sunucularını satın almak yerine AWS'den ihtiyacın kadar kapasite kiralar, kullandığın kadar ödersin. Platform Mühendisi olarak neredeyse her şeyi AWS üzerinde çalıştırırsın.

Temel Kavramlar
Region      → fiziksel veri merkezi bölgesi (eu-west-1 = İrlanda, us-east-1 = ABD Virginia)
AZ          → Availability Zone — bir region içindeki bağımsız veri merkezi
VPC         → Virtual Private Cloud — senin özel ağ alanın
IAM         → Identity and Access Management — kim ne yapabilir
EC2         → Elastic Compute Cloud — sanal sunucu (VM)
S3          → Simple Storage Service — sınırsız nesne depolama
RDS         → Relational Database Service — yönetilen veritabanı
ELB         → Elastic Load Balancer — yük dengeleyici
EKS         → Elastic Kubernetes Service — yönetilen Kubernetes
Lambda      → sunucusuz fonksiyon çalıştırma
CloudWatch  → izleme, loglar, alarmlar
Route 53    → DNS servisi
Region ve AZ İlişkisi
eu-west-1 (İrlanda)
  ├── eu-west-1a   ← veri merkezi 1
  ├── eu-west-1b   ← veri merkezi 2
  └── eu-west-1c   ← veri merkezi 3

# her AZ bağımsız güç, soğutma, ağ altyapısına sahip
# bir AZ çöktüğünde diğerleri çalışmaya devam eder
# production'da her zaman birden fazla AZ kullan

# senin bölgelerin muhtemelen:
eu-west-1   ← Avrupa (İrlanda) — Inpart gibi İngiliz şirketler için yaygın
us-east-1   ← ABD (Virginia) — AWS'nin ana bölgesi, en ucuz fiyatlar

A4 S3 — Nesne Depolama AWS ▼

S3 (Simple Storage Service), AWS'nin nesne depolama servisidir. Dosyaları sınırsız miktarda depolarsın — statik web siteleri, uygulama build'leri, log arşivleri, Terraform state dosyaları, medya dosyaları. Neredeyse her AWS mimarisinde S3 vardır.

Temel Kavramlar
Bucket    → en üst düzey kapsayıcı. Adı dünya genelinde benzersiz olmalı.
Object    → bir dosya + metadata. Boyut sınırı yok (teorik).
Key       → nesnenin yolu/adı. Klasör mantığı simüle eder.
Prefix    → key'in klasör gibi davranan bölümü

# örnek:
Bucket:  inpart-deploy-artifacts
Object:  builds/connect-playwright/v1.2.3/report.html
Key:     builds/connect-playwright/v1.2.3/report.html
Prefix:  builds/connect-playwright/
S3 CLI Komutları
# bucket oluştur
aws s3 mb s3://benim-bucket-adim --region eu-west-1
# → AWS S3 | aws s3 mb = make bucket, --region zorunlu — EZBER

# bucket'ları listele
aws s3 ls

# bucket içeriğini listele
aws s3 ls s3://benim-bucket-adim/

# dosya yükle
aws s3 cp dosya.txt s3://benim-bucket-adim/
# → AWS S3 | aws s3 cp = kopyala — yerel→S3 veya S3→yerel çalışır — EZBER

# klasör yükle (recursive)
aws s3 cp dist/ s3://benim-bucket-adim/builds/v1.0/ --recursive

# dosya indir
aws s3 cp s3://benim-bucket-adim/dosya.txt .

# sync — sadece değişenleri yükle (build artifacts için ideal)
aws s3 sync dist/ s3://benim-bucket-adim/site/ --delete
# → AWS S3 | aws s3 sync --delete = sadece değişenleri yükle, fazlaları sil — CI/CD deploy kalıbı — EZBER

# dosya sil
aws s3 rm s3://benim-bucket-adim/dosya.txt

# bucket sil (önce boşaltman gerekir)
aws s3 rb s3://benim-bucket-adim --force

Monitoring — 7 Bölüm
M1 Temel Kavramlar Monitoring ▼

Monitoring, sisteminin sağlığını sürekli izlemektir. Kullanıcılar sana "site çalışmıyor" yazmadan önce sen zaten bilmelisin. Platform Mühendisi olarak monitoring kurmak, alarm tanımlamak ve olaylara müdahale etmek temel sorumluluklarından biridir.

Üç Temel İzleme Sütunu
Metrikler (Metrics)
  → sayısal ölçümler: CPU %71, bellek 3.2GB, istek/saniye 450
  → "ne kadar" sorusunu yanıtlar
  → Prometheus, CloudWatch, Datadog

Loglar (Logs)
  → zaman damgalı metin kayıtları: "ERROR: DB bağlantısı kesildi"
  → "ne oldu" sorusunu yanıtlar
  → Grafana Loki, ELK Stack (Elasticsearch + Logstash + Kibana), CloudWatch Logs

İzler (Traces)
  → tek bir isteğin sistemde aldığı yol
  → "nerede yavaşladı" sorusunu yanıtlar
  → Jaeger, AWS X-Ray, OpenTelemetry
Monitoring Olmadan vs Monitoring ile
Monitoring olmadan:
  kullanıcı: "site çalışmıyor"
  sen: sunucuya SSH → logları oku → nedenini bulmaya çalış
  geçen süre: 20-60 dakika

Monitoring ile:
  alarm: "API hata oranı %0.1'den %5'e çıktı" → bildirim geldi
  dashboard: hata hangi endpoint'ten, hangi sunucudan?
  log: tam hata mesajı ve stack trace
  geçen süre: 2-5 dakika müdahale

import { Registry, Counter, Histogram } from 'prom-client'

const registry = new Registry()

const httpRequests = new Counter({
  name: 'http_requests_total',
  help: 'Toplam HTTP istek sayısı',
  labelNames: ['method', 'path', 'status'],
  registers: [registry]
})

const httpDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP istek süresi (saniye)',
  labelNames: ['method', 'path'],
  buckets: [0.01, 0.05, 0.1, 0.5, 1, 5],
  registers: [registry]
})

# middleware olarak ekle
app.use((req, res, next) => {
  const end = httpDuration.startTimer({ method: req.method, path: req.path })
  res.on('finish', () => {
    httpRequests.inc({ method: req.method, path: req.path, status: res.statusCode })
    end()
  })
  next()
})

# /metrics endpoint'i aç — Prometheus buradan okur
app.get('/metrics', async (req, res) => {
  res.set('Content-Type', registry.contentType)
  res.send(await registry.metrics())
})

M6 SLI, SLO, SLA Monitoring ▼

Monitoring sadece teknik araçlar değildir. Sistemin ne kadar güvenilir olması gerektiğini de tanımlaman gerekir. Google'ın SRE (Site Reliability Engineering) ekibinin geliştirdiği SLI/SLO/SLA modeli, güvenilirliği ölçülebilir hedefler haline getirir.

SLI → SLO → SLA
SLI — Service Level Indicator (Gösterge)
  → Sistemin güvenilirliğini ölçen metrik
  → "Son 30 günde isteklerin yüzde kaçı başarılı?"
  → Örnek: %99.7

SLO — Service Level Objective (Hedef)
  → SLI için belirlenen hedef
  → "Başarı oranı %99.5 veya üstünde olmalı"
  → Ekip içi hedef — müşteriyle paylaşılmayabilir

SLA — Service Level Agreement (Anlaşma)
  → Müşteriyle imzalanan yasal sözleşme
  → "Aylık uptime %99.9 garantisi — ihlalde %10 kredi"
  → SLO'dan daha muhafazakar olur (hedefiniz %99.9 ise SLA %99.5)
Uptime Oranları — Gerçek Sayılar
UptimeAylık KesintiYıllık KesintiYaygın Adı
%99.0~7.3 saat~3.65 günİki dokuz
%99.9~43.8 dakika~8.7 saatÜç dokuz
%99.95~21.9 dakika~4.4 saatÜç buçuk dokuz
%99.99~4.4 dakika~52 dakikaDört dokuz
%99.999~26 saniye~5.3 dakikaBeş dokuz

# SLO %99.9 → aylık 43.8 dakika kesinti hakkı

  → Evet → yeni özellik deploy edebilirsin
  → Hayır → deployment dondur, güvenilirlik çalış

      sum(rate(http_requests_total[1h]))
